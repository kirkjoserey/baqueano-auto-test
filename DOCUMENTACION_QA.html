Documentación Técnica

Worker Service en C# que ejecuta pruebas automatizadas de interfaz de usuario (UI testing) sobre el backend Java EE Baqueano, cubriendo tres viewports: PC Desktop, Tablet y Celular.

🔷 .NET 8 Worker Service
🌐 Selenium WebDriver 4.27
🗄 SQLite
📸 Capturas automáticas
📊 Reporte HTML
📱 Responsive Testing
🏠

¿Qué es este proyecto?

BaqueanoAutoTest es un programa de testing automatizado que se conecta al sistema web Baqueano y realiza pruebas funcionales sobre sus módulos sin intervención humana. Cada vez que se ejecuta, limpia los resultados anteriores, corre todas las pruebas, captura pantallas y genera un reporte HTML interactivo con los resultados clasificados por dispositivo.

🤖
Totalmente autónomo
Se ejecuta con un solo comando. No requiere intervención manual durante las pruebas.
📱
3 viewports
Prueba la misma funcionalidad en Desktop (PC), Tablet (768px) y Celular (390px).
📊
Reporte visual
Genera un único archivo HTML con grilla de capturas, filtros y estadísticas.
🗄
Historial en SQLite
Todos los resultados quedan guardados en una base de datos local.
📋

Patrón Page Object Model (POM)

Cada pantalla del sistema tiene su propia clase en Pages/ que encapsula los selectores y las acciones. Los tests (Tests/) usan esas clases sin conocer los detalles del HTML. Esto hace que un cambio en la UI solo requiera modificar el Page Object, no los tests.

Cómo ejecutar

  • 1
    Levantar el backend Baqueano Asegurarse de que el servidor Java EE esté corriendo en http://localhost:8080/baqueano y sea accesible desde el navegador.
  • 2
    Abrir terminal en la carpeta del proyecto cd C:\Users\james\source\repos\baqueanoAutoTest
  • 3
    Compilar (opcional, para verificar) dotnet build
  • 4
    Ejecutar las pruebas dotnet run
    El programa abre Chrome automáticamente y comienza a ejecutar todas las fases.
  • 5
    Ver resultados Al finalizar, se genera el archivo TestReport_YYYYMMDD_HHmmss.html en la carpeta del ejecutable (bin\Debug\net8.0\). Abrirlo en cualquier navegador.
⚠️
Al iniciar, el programa borra automáticamente todos los resultados anteriores de la base de datos, todas las capturas de pantalla y el reporte HTML previo. Cada ejecución parte desde cero.

Ejecutar en modo headless (sin ventana)

Útil para servidores CI/CD donde no hay pantalla disponible:

JSONappsettings.json
"Headless": true

🖥️ Desktop ChromeDriver estándar (--start-maximized) Pantalla completa Chrome desktop sin prefijo 🖥️ Desktop

ℹ️
Cuando una fase encuentra que un elemento de la UI no es accesible (por ejemplo, el menú lateral colapsado en mobile), el test registra FAIL en esa fase específica sin afectar las demás. Eso es información válida sobre problemas de responsive.

Módulo: Perfiles

Cantidad configurable via TotalPerfilesTests (default: 40). La distribución se calcula automáticamente:

🧭
NAV (2 fijos)
TC-PER-NAV-01: navega vía sidebar
TC-PER-NAV-02: navega vía URL directa
➕
ALTA — 40%
Crea perfiles con nombre, descripción y estado Activo/Inactivo
✏️
MODIFICAR — 40%
Edita los perfiles creados cambiando sus datos
🗑️
ELIMINAR — 20%
Borra los perfiles creados y verifica que desaparezcan
👥

Módulo: Usuarios

Cantidad configurable via TotalUsuariosTests (default: 12). Incluye prueba de login por ventana nueva.

BloqueTestsDescripción
NAV2 fijosSidebar y URL directa
ALTA40% del totalCrea usuarios con nombre, apellido, email, perfil (ADMIN/CONSULTA/GESTOR) y estado activo
LOGIN30% de los creadosAbre una ventana nueva, prueba el login de cada usuario creado y cierra la ventana
MODIFICAR40% del totalEdita datos del usuario (excepto el usuario admin)
ELIMINAR20% del totalElimina usuarios (nunca elimina admin)
🛡️
El usuario admin está protegido por doble capa: la página no permite editarlo ni eliminarlo, y los tests lo filtran antes de intentarlo.
🔧

Módulo: Parámetros

Cantidad configurable via TotalParametrosTests (default: 25). Misma distribución que Perfiles (40/40/20).

Cada parámetro se crea con clave, valor, descripción y estado (Activo/Inactivo). Los tests verifican que el registro aparezca en la tabla tras cada operación.

Reporte HTML

Al finalizar todas las fases se genera un único archivo TestReport_YYYYMMDD_HHmmss.html. Es un archivo autónomo (sin dependencias externas) que se puede abrir en cualquier navegador.

📟
Pestañas por dispositivo
Filtrar por PC Desktop, Tablet o Celular con un clic. Cada pestaña muestra su propio conteo PASS/FAIL y porcentaje.
🔍
Zoom en imágenes
Al pasar el mouse sobre una captura se amplía (scale 1.6×). Clic abre la imagen en pantalla completa (lightbox).
📄
Paginación 3×3
La grilla muestra 9 tests por página con navegación numérica.
🏷️
Badges identificadores
Cada tarjeta muestra: categoría, PASS/FAIL, y el dispositivo (🖥️ Desktop / 📟 Tablet / 📱 Celular).

Interpretación del color de pestañas

Color del porcentajeSignificado
Verde100% de tests en PASS
NaranjaEntre 50% y 99% en PASS — hay fallas menores
RojoMenos del 50% en PASS — hay fallas críticas

Clasificación de errores

Cuando un test falla, el mensaje en el reporte incluye un prefijo que indica la causa raíz:

PrefijoCausaEjemplos
[HERRAMIENTA] Problema de Selenium al interactuar con la UI Elemento no encontrado, elemento bloqueado, timeout de espera, ventana cerrada inesperadamente
[ASERCION] El test completó pero el resultado no es el esperado La página no cargó, el registro no aparece en la tabla, el conteo no bajó tras eliminar
[PROGRAMACION] Error en la lógica interna del test NullReferenceException, InvalidOperationException, lógica de código incorrecta
💡
[HERRAMIENTA] suele indicar que la UI cambió (selector desactualizado) o que hay lentitud de red. [ASERCION] indica que la funcionalidad del sistema falló. [PROGRAMACION] indica un bug en el propio código de testing.

Agregar un nuevo módulo de tests

  • 1
    Crear el Page Object en Pages/ Implementa los selectores y acciones de la nueva pantalla.
  • 2
    Crear la clase de test en Tests/ Implementar la interfaz ITest con el método RunAsync(IWebDriver driver).
  • 3
    Registrar en Program.cs
    C#Program.cs
    // Agregar al final de la lista de tests:
services.AddTransient<ITest, MiNuevoTest>();
  • 4
    Agregar conteos en appsettings.json Agregar "TotalMiModuloTests": 10 en las tres secciones (TestSettings, TabletSettings, MobileSettings).
ℹ️
El nuevo módulo se ejecutará automáticamente en las tres fases (Desktop, Tablet, Celular) sin ningún cambio adicional en el TestRunner.

Solución de problemas frecuentes

ProblemaCausa probableSolución
ChromeDriver no inicia Versión de Chrome ≠ versión del ChromeDriver Ejecutar dotnet restore para actualizar el paquete ChromeDriver
WebDriverTimeoutException en login El backend tarda en cargar o el SPA demora en redirigir Aumentar ImplicitWaitSeconds a 15 o 20 en appsettings.json
Tests de mobile/tablet fallan todos El DeviceName configurado no existe en esta versión de Chrome Dejar DeviceName: "" para que use Width/Height automáticamente
Toasts bloquean los clicks Notificaciones Sonner flotando sobre los botones Ya está manejado automáticamente por WaitForToastsToDisappear(). Si persiste, aumentar el timeout de toast (actualmente 6s)
Modal de Contactos no se detecta React no genera role="dialog" estándar El sistema detecta el modal por los botones de estado (NUEVO/LEIDO/etc.), no por el contenedor. Si los botones cambian de texto, actualizar StateButtonsXPath en ContactosPage.cs
Reporte HTML sin imágenes Las capturas y el HTML están en distintas carpetas Abrir el reporte desde la carpeta bin\Debug\net8.0\, no moverlo a otra ubicación
Error al compilar: NETSDK1022 Archivos duplicados en el .csproj Eliminar la línea <Content Include="appsettings.json"> del .csproj
